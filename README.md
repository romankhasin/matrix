# matrix

Ранкер площадок для медиаплана: скоринг рекламных площадок по стоимости конверсии (CPA), качеству постклика и CPM, с настраиваемыми весами.

## Структура

- `dashboard/index.html` — интерактивный дашборд (слайдеры весов, рейтинг площадок в виде сортируемой таблицы, фильтры: месяцы, блок ЖК, тип конверсии); копия в `docs/index.html` для GitHub Pages. Данные вставляются в файл между маркерами `/*DATA:START*/ … /*DATA:END*/`
- `scripts/build_dashboard_data.py` — **основной сборщик данных для дашборда**: расход (`data/spend_source.xlsx`, разбивка по колонке «Проект») + конверсии (сделки, встречи, звонки из двух сводных xlsx: май–июль и август) + постклик (`data/metrika_*.csv`) → `data/dashboard_data.json` и вставка в `dashboard/index.html` и `docs/index.html`. Токены ЖК и их блоки (`TOKEN_BLOCK`, `PROJECT_BLOCK`) — в начале скрипта
- `scripts/fetch_metrika.py` — выгрузка через Yandex Metrika Reporting API (заблокирован в этом окружении egress-прокси, не запускался)
- `scripts/parse_metrika.py` — парсинг ручных выгрузок отчёта "Метки UTM" за август (`data/metrika_raw_*.tsv`) в `data/metrika_august2026.csv`
- `scripts/build_metrika_multi.py` — то же самое, но для май/июнь/июль (вход: `data/metrika_raw2/{zhk,commerce}_<month>_agg.tsv`, уже агрегированные по площадкам через JS-экстракцию в браузере — API и вручную-по-строкам copy-paste не использовались)
- `scripts/extract_bi_deals.py` — извлечение целевых конверсий (сделок) из BI-выгрузки клиента, август (одномесячный файл)
- `scripts/extract_bi_deals_multi.py` — то же самое для комбинированной выгрузки БИ за май–июль (один файл, разбивка по колонке «Месяц», другой сдвиг колонок)
- `scripts/normalize_platforms.py` — словарь нормализации названий площадок (одна и та же площадка часто по-разному называется в разных выгрузках)
- `scripts/merge_data.py`, `scripts/build_merged_august.py` — сведение расходов + BI в единую таблицу за август
- `scripts/build_merged_multi.py` — то же самое для май/июнь/июль (расход берётся из того же файла "Ежемесячная статистика MI // Level", колонки ищутся по заголовку, а не по фиксированному индексу — у мая расширенный набор колонок)
- `scripts/merge_with_metrika.py`, `scripts/merge_with_metrika_multi.py` — добавление постклик-метрик (отказы/время на сайте) в сведённую таблицу
- `data/` — исходные и промежуточные данные (⚠️ содержит реальные цифры клиента — репозиторий публичный)

## Сделки с форматом («PBi для стратегии тест.xlsx»)

Лист «участия в сделках» — конверсии за январь 2025 – июль 2026, но UTM-кампания в файле уже
разложена Excel'ем по колонкам (без единой раскладки: порядок и число колонок гуляют от строки
к строке, иногда кусок кампании остаётся нерасщеплённым в одной ячейке через `|` или `~`).

`load_deals_tokenized()` в `build_dashboard_data.py` не полагается на номер колонки: собирает
все непустые ячейки строки в список токенов и ищет в нём:
- **блок ЖК** — первый токен из `TOKEN_BLOCK` (`lg`, `sel`, `zv`, …);
- **площадку** — сначала пары соседних токенов (`novostroy`+`m` → `novostroy-m`, `yandex`+`go` →
  `yandex_go`), потом одиночные, и только среди **уже занесённых** названий — тех, что реально
  встречаются в `spend_source.xlsx` и в бюджетном своде за этот же запуск (плюс словарь
  `normalize_platforms.ALIASES`). Площадки, которых в бюджетах ещё нет, в подбор не попадают;
- **формат** — точное совпадение токена со словарём `FORMAT_MAP` (video/olv/ctv → video;
  banner/banners/richmedia → banner; tgb; branding/brand);
- **месяц и год** — токен вида `<mon><ГГ>` (сен25, jan26…), включая полные названия `june`/`july`.

Строки с годом 2023/2024 отбрасываются той же логикой, что и в остальных источниках. Из 2182
строк распознано 2153 (98,7%); 23 потеряны из-за неизвестной площадки, 6 — без токена месяца.

Сделки суммируются в те же строки `(блок, площадка)`, что и бюджет, добавляя разбивку по формату
(`fmt: {video, banner, tgb}`) — видно и в бюджетной таблице (для месяцев без Метрики), и как
источник для дальнейшего подключения полного рейтинга.

Запуск: `build_dashboard_data.py … --deals-tokenized "<PBi для стратегии тест.xlsx>"`.

## Метрика без отдельных колонок площадки/месяца («Метки UTM-<период>.xlsx»)

У этого формата выгрузки только 4 колонки: UTM Campaign, Визиты, Отказы, Время на сайте — нет
UTM Source и нет разбивки по месяцу визита. `load_metrika_campaign()` достаёт из UTM-кампании
то же, что и `load_deals_tokenized()`: блок (`campaign_block`), площадку (`token_platform`, среди
уже занесённых) и месяц/год. Дополнительно, специально для этого источника, есть запасной разбор
месяца: диапазоны вида `jan25-may25` (берётся первый месяц) и голый месяц без года
(`..._discount_feb`, год — из имени файла, то есть из периода отчёта).

Даёт сразу оба вида постклика: по площадке в целом (`post`) и по паре «блок × площадка»
(`postb`) — из одного файла. Бюджетный месяц, для которого нашлась хотя бы какая-то Метрика,
помечается `"full": true` — для него включается обычный рейтинг (Score), а не бюджетная таблица.

Все 12 месяцев 2025 года закрыты такими выгрузками — шесть файлов по жилой недвижимости
(1-2 месяца в каждом) плюс один годовой файл по коммерции (business.level, счётчик отдельный
от жилых ЖК); распознано ~92% из 6,82 млн визитов. Блок «Коммерция» (Воронцовская, Нижегородская
W, Свободы) до этого файла почти не ранжировался — Метрики по нему не было. Потери — кампании
без определяемого месяца (телеграм-рассылки, email, отдельные виджеты) и площадки, которых ещё
нет в бюджетах (Wink, Premier, VideoNetwork без уточнения, Telegram Ads, VK Ads interactive/pin,
MyTarget и т.п. — их специально не добавлял в алиасы, раз их нет в уже занесённых расходах).

Запуск: `build_dashboard_data.py … --metrika-campaign "<файл1>" "<файл2>" …` — можно перечислить сколько угодно файлов за разные периоды одним запуском.

Покрыты оба года: 2025-й (семь файлов, см. выше) и 2026-й (четыре файла — янв-мар, апр-июн,
июл-авг, плюс годовой business.level). Итого 11 файлов, ~12,2 млн визитов, распознано ~92%.
Теперь каждый месяц с мая 2025 по август 2026 (кроме отдельных случаев без покрытия) ранжируется
полноценно — «full: true» ставится, если для месяца нашлась хоть какая-то Метрика (через
`metrika_campaign_postb`), независимо от источника сделок.

## Текущее состояние данных

Дашборд временно содержит **только бюджеты** (расход, показы, клики) за все месяцы — конверсии (сделки/встречи/звонки) и постклик (Метрика) убраны из данных до получения новых выгрузок. Пересобрать с бюджетом без конверсий:

```
python3 scripts/build_dashboard_data.py --spend data/spend_source.xlsx \
  --budget "<Бюджеты свод 25-26.xlsx>" --out data/dashboard_data.json \
  --inject dashboard/index.html docs/index.html
```

`--conv-mayjul`, `--conv-aug`, `--metrika-dir`, `--metrika-utm`, `--deals-dated` теперь необязательны — без них месяцы мая–августа 2026 идут тем же бюджетным режимом, что и остальные (расход из `spend_source.xlsx`, без конверсий и постклика).

## Фильтр старых кампаний

Из всех источников конверсий (сделки, встречи, звонки — и в майско-августовских BI-выгрузках, и в файле с точными датами) отбрасываются строки, где в названии UTM-кампании есть токен года 2023 или 2024 (например `..._oct23`, `..._sep24`). Такие конверсии относятся к кампаниям, которые давно не размещаются, и искажают CPA актуальных площадок. Фильтр — `is_stale_campaign()` / `STALE_CAMPAIGN_YEARS` в `build_dashboard_data.py`, применяется в `load_conversions()` и `load_deals_dated()`. На постклик (визиты/отказы/время из Метрики) фильтр не влияет — это отдельный источник.

## Скрытие площадок из ранкера

Кнопка ✕ рядом с названием площадки (в основной таблице, в любом режиме) скрывает её полностью:
она перестаёт учитываться в `aggregate()` ещё до нормализации Score/CPM, до сумм в «Итого» и до
боковых списков — как будто её нет в данных этого месяца. Список скрытых площадок — панель
«Скрытые площадки» в сайдбаре (видна только когда список не пуст), возврат — кнопкой ↺ на чипе.
Хранится в `localStorage` этого браузера (ключ `hiddenPlatforms`), не в данных — у каждого, кто
открывает дашборд, свой список.

## Разбивка площадок на Video / Display — попробовали и откатили

Была попытка раскладывать площадку на «Площадка · Видео» / «Площадка · Баннеры» там, где формат
виден в сыром названии (`Mts.ru OLV`, `qbid banner` и т.п.). Столкнулись с тем, что у площадки
часть строк промаркирована, а часть нет — наивное разбиение по строкам оставляло третью,
немаркированную строку рядом с её же видео/баннерами (например, «qbid», «qbid · Видео» и
«qbid · Баннеры» одновременно). Решение (первый проход по всем месяцам и обоим источникам расхода,
чтобы понять формат площадки в целом — `format_only`/`format_ratio`) само по себе работало, но
заодно показало, что у ряда площадок (МТС, Avito, Astralab, Digital Alliance, Adspector) в данных
вообще ни разу не встречается второй формат — то есть «МТС» в ранкере стал бы только «МТС · Видео»,
без «МТС · Баннеры», что для площадки, у которой на самом деле могли быть и баннеры, выглядит как
потеря данных, а не их уточнение. Отменили по просьбе — вернулись к единой площадке без разбивки по
формату, обдумаем подход к этому отдельно (например, явный список форматов по площадке вместо
автоопределения по словам в названии).

У видео/OLV-размещений в бюджетном своде часто нет кликов вообще (трекаются «досмотры», а не
клики) — `cost > 0`, `impr > 0`, но `clicks = 0`. Усреднение постклика (`aggregate()` в
`dashboard/index.html`) изначально было взвешено по кликам, поэтому такие строки никогда не
получали веса для отказов/времени на сайте и структурно выпадали из рейтинга в раздел «Есть расход
и конверсии, нет данных Метрики» — даже когда Метрика по площадке реально была. Это исправление
осталось в силе (не связано с разбивкой по формату): вес усреднения — клики, а если `clicks = 0` —
показы (`const w = r.clicks > 0 ? r.clicks : r.impr`). Нашли на примере МТС за август 2025
(19 сделок, 40 встреч, 0 кликов) — после фикса попадает в рейтинг.

## Переходящий выбор месяцев через границу года

Переключение года в верхнем фильтре — навигация по сетке месяцев, а не сброс выбора: можно
отметить, например, декабрь 2025 и январь 2026 одновременно (переключиться на 2025, отметить
декабрь, переключиться на 2026, отметить январь — оба останутся выбраны). У года, где что-то
выбрано, но сейчас не открыт, показывается подпись «выбрано: N». При первом переключении на год,
где ещё ничего не выбрано, для удобства сразу подставляется его последний месяц.

## Динамика CPA по площадке

Отдельная мини-панель под основной таблицей (не связана с фильтрами год/месяц/блок наверху):
выбор площадки, блока, типа конверсии и произвольного набора месяцев (чипы, весь список из
20 месяцев) — столбцы показывают число конверсий выбранного типа за месяц, линия — CPA. Строится
на голом SVG (без библиотек), генерируется в `renderTrend()` в `dashboard/index.html`. Площадки
в выпадающем списке отсортированы по алфавиту (название через `name()`), а не по расходу. Числа
над столбцами и точками рисуются с отступом над фигурой (не у базовой линии), чтобы не
перекрывались друг с другом при любом соотношении конверсий/CPA.

Тип конверсии — отдельный переключатель (`trendConv`, те же три типа, что и «Все сразу» в основном
фильтре наверху — `CONV_ALL_KEYS`: сделки/встречи — «Участие», звонки — «Первый клик, 90 дн»).
Выбирается один тип за раз, без смешивания — та же причина, что и везде в этом дашборде: разные
модели атрибуции нельзя складывать в одну цифру, не исказив её смысл.

Под этим графиком — «Накопленный CPA» (`renderCumulative()`, та же площадка/блок/месяцы): столбцы —
расход нарастающим итогом по выбранным месяцам, линия — CPA по накопленным на тот момент расходу
и сделкам (`cumulativeSeries()` в `dashboard/index.html`). Показывает, как CPA «устаканивается»
по мере того, как в периоде накапливается бюджет и успевают закрыться сделки — в отличие от
помесячного CPA на графике выше, тут нет резких скачков от месяцев с 1-2 сделками.

## Встречи и звонки («PBi для стратегии (2).xlsx»)

4 листа «Кампания» + «Атрибутировано»: «встречи участия» (модель «Участие», как у сделок) и
«звонки 1й клик 90 дн» (модель «Первый клик, 90 дн»). Листы «сделки 1й клик 90 дн» (32 строки) и
«встречи 1й клик 90 дн» (105 строк) — та же модель «Первый клик, 90 дн», а не «Участие», как у
основных сделок/встреч — подключены как два **отдельных** типа конверсии, `deal_fc`/`meet_fc`
(«Сделки (1-й клик)» / «Встречи (1-й клик)»), а не прибавлены к сделкам/встречам: окна атрибуции
не смешиваем в одной цифре (та же логика, что и раньше). Всего распознано 39 сделок(1кл) и 136
встреч(1кл) (`MC_SHEETS`, `load_deals_meetings_calls()` в `build_dashboard_data.py`).

Формат кампании — «ЖК X | площадка | формат | токен» (как в первых BI-выгрузках), площадка
берётся напрямую из второго сегмента через `campaign_platform()`, блок — через `campaign_block()`,
месяц/год — из последнего сегмента через `token_month_year()`. Из 4868 распознанных строк без
площадки не осталось ни одной, 21 потеряна без определяемого месяца.

Переключатель «Сделки / Встречи / Звонки / Сделки (1-й клик) / Встречи (1-й клик) / Все сразу» и
все пять колонок конверсий — в таблице рейтинга. «Все сразу» по-прежнему означает «сделки + встречи
+ звонки», как и раньше — `deal_fc`/`meet_fc` в эту кнопку не входят и включаются только вручную
отдельным чекбоксом, иначе часть договоров задвоилась бы (один и тот же договор может попасть и в
«Участие», и в «Первый клик» одновременно, под разными площадками).

Запуск: `build_dashboard_data.py … --meetings-calls "<PBi для стратегии (2).xlsx>"`.

## Блоки ЖК и конверсии

Блок определяется по токену в начале UTM-кампании (`sp_yandex_…`, `LM_Медийка_…`), у расходов — по колонке «Проект»:

- **Комфорт** — Лесной (gvl), Мечникова (lmech-rspb), Нижегородская (ng), Селигерская (sel), Южнопортовая (sp), Нагатинская (ln), Стрешнево (ls), Звенигородская (zv), Мичуринский (lm) — «Комфорт+» объединён с «Комфорт» в один блок
- **Бизнес** — Академическая (ak), Бауманская (lb), Войковская (lv), Волга (lvol-rnn), Павелецкая Сити (pc), Причальный (pr)
- **Делюкс** — Саввинская 17 / 27 (sav)
- **Коммерция** — Воронцовская (vr), Нижегородская W (lwnizh-rmsk), Свободы (lwsv)
- **Бренд** — Левел Групп, Остатки, Премиум, Регионы, Зонтик (lg …)
- **Без блока** — токен не найден или проект не в списке (сейчас — разные нераспознанные кампании: Criteo, dv360, YouTube и т.п.)

Типы конверсий и модели атрибуции (у типов разные, подписаны в интерфейсе): сделки и встречи — «Участие», звонки — «Первый клик, 90 дн». Строки сделок/встреч с моделью «первый клик» отбрасываются. Августовские выгрузки ПБА (медийка) и PBI (программатик) суммируются. При выборе нескольких типов конверсии складываются, это не дедуплицированный итог.

Постклик (отказы, время на сайте) считается по паре «блок × площадка» из выгрузок Метрики «Метки UTM» (UTM Source × UTM Campaign × месяц визита; два файла — счётчик ЖК и счётчик Коммерция; блок берётся из токена кампании). Если по блоку в месяце меньше 200 визитов или меток нет — используется значение по площадке в целом (`data/metrika_*.csv`). ⚠️ В выгрузку с кампаниями попадают только визиты с токеном ЖК: например, у Яндекса в блочных цифрах ~25% трафика (Карты, Дзен, Промопейджес без токена не учтены). Выгрузки запускаются как `--metrika-utm <файл ЖК> <файл Коммерция>` в `build_dashboard_data.py`.

Названия площадок в расходах и Метрике приведены к одному виду в `normalize_platforms.py` (например, `avito-ads` → Avito, `inlab` → Innovation Lab, `da` → Digital Alliance).

**Яндекс** разбит на пять отдельных площадок вместо одной «Яндекс (медийка)»:
- `yandex` — медийка/видео (`media.yandex`, `video.yandex` и их варианты);
- `yandex_promopages` — Яндекс Промостраницы;
- `yandex_maps` — Яндекс Карты/гео (карты, метки, апартаменты, smartcamera);
- `yandex_weather` — Яндекс Погода;
- `dzen` — Дзен.

Расход в бюджетах разбит отдельно для **Промостраниц** (`Promopages.yandex`) и **Дзена**
(`Дзен`, `Дзен статья`) почти во всех месяцах, и для **Карт** (`Geomedia.yandex`) в нескольких —
эти три видны в блоке «Что не попало в рейтинг» (расход есть, сделок нет: Дзен и Промостраницы
входят в топ-8 по расходу за 2025 год). У **Погоды** отдельного расхода в бюджетах нет — только
визиты, поэтому она нигде не отображается, пока не появится своя строка расхода.

## Бюджеты за прошлые месяцы (фев 2025 – апр 2026)

Источник — свод «Бюджеты свод 25-26.xlsx» (листы «<Месяц> <год>»), берутся столбцы **D / E / G = Расход / показы / клики**. Расход в своде без НДС, поэтому **умножается на 1,2** (как «с НДС» в месяцах с мая 2026). Апрель 2026 берётся из этого свода. Недельные рабочие листы (`05-10.25`, `Append2`) пропускаются. Опечатки в названиях проектов исправляются (`PROJECT_ALIAS`: «Южнопоротовая», «Level Group», «Саввинские»).

Для этих месяцев нет конверсий и Метрики, поэтому в дашборде показывается таблица бюджета (расход, доля, показы, клики, CTR, CPM, CPC) без рейтинга. В дашборде выбираются год, затем месяцы; если среди выбранных месяцев есть бюджетный, включается бюджетный режим. В листах свода есть колонка «формат» (display / video) — под будущую разбивку видео/баннер.

Запуск: `build_dashboard_data.py … --budget "<Бюджеты свод 25-26.xlsx>"`.

## Логика скоринга

Score = взвешенная сумма нормализованных метрик (0–100):
- **CPA** — стоимость выбранной конверсии (сделки / встречи / звонки — любой тип или их сумма)
- **Постклик** — отказы + время на сайте (Яндекс.Метрика)
- **CPM** — стоимость 1000 показов

Веса настраиваются в дашборде.

### Вес типа конверсии в CPA/Score

При выборе нескольких типов конверсии сразу («Все сразу» или любая комбинация) сделка, встреча
и звонок по умолчанию считались равнозначными — один звонок повышал «Конверсии» для CPA ровно
так же, как одна закрытая сделка, хотя по ценности для бизнеса это разные события. Добавлены
ползунки веса (фильтр «Конверсия» в шапке, видны только когда выбрано ≥2 типов): Сделки 100%,
Встречи 40%, Звонки 15% по умолчанию (сделка важнее встречи, встреча важнее звонка — настраивается
на лету). Вес применяется только к величине, по которой считается CPA (`a.cpaConv` в
`aggregate()`, `dashboard/index.html`) — колонки «Конверсии»/«Сделки»/«Встречи»/«Звонки» в таблице
по-прежнему показывают «сырые», невзвешенные количества. При выборе одного типа конверсии вес не
действует (взвешивать нечего).

## Визуальный редизайн — в духе Tableau Server

Цветовые токены, типографика и форма компонентов обновлены под язык корпоративных BI-инструментов
(визуальный ориентир — интерфейс Tableau Server/Cloud: холодная палитра, фирменный синий, плотные
данные, компактные «pill»-фильтры):

- **Цвета** — почти везде это просто замена значений уже существующих CSS-переменных
  (`--accent`, `--bg`, `--surface`…) в `:root`/`[data-theme="light"]`, поэтому пересобирать логику
  не пришлось: синий (`--accent`) стал основным цветом действия вместо янтарного — активные чекбоксы,
  Score, сортировка, слайдеры, ссылки. Светлая тема стала холоднее (голубовато-серый фон вместо
  тёплого кремового), тёмная — чуть глубже. Добавлен `--orange` про запас (пока нигде не используется).
- **Шрифт** — засечки Fraunces в заголовках заменены на Inter (жирнее, `font-weight:800` у `<h1>`) —
  читается более технологично, без «редакционного» оттенка. IBM Plex Mono для чисел в таблице и
  графиках оставлен — так колонки с цифрами выглядят точнее.
- **Форма** — кнопки-«таблетки» (`.presets`, `.collapse-btn`, `.hidden-chip`, ранее `border-radius:100px`)
  стали скруглёнными прямоугольниками (7px) — ближе к тому, как в Tableau выглядят сами «pills» на
  полках. У панелей (`.panel`) появилась лёгкая тень (`--shadow-panel`) вместо плоской заливки — чуть
  более «приподнятый», предметный вид карточек.
- **Верхняя плашка** (`.app-bar`) — тёмно-синяя полоса на всю ширину окна (не зависит от темы, как
  верхнее меню в enterprise-инструментах) с мини-лого (SVG «столбики» — отсылка к рядам Tableau, но
  не копия логотипа) и хлебной крошкой «Левел Групп / Медиаплан».

Заодно нашли и починили то, что раньше просто не проявлялось: в файле не было
`<meta name="viewport">`, поэтому на мобильных страница всегда рендерилась как «уменьшенная
десктопная» (эффективная ширина 980px) — добавили тег и выяснилось, что при настоящей узкой ширине
таблица рейтинга (много колонок, `white-space:nowrap`) раздвигала всю страницу вбок, потому что
grid-колонка `main` не имела `min-width:0` (так браузеры по умолчанию не дают элементу сжаться уже
своего `min-content`). Добавили `min-width:0` на `.layout > aside, .layout > main` и
`overflow-x:hidden` на `html`/`body` как страховку — на мобильных ширина больше не «убегает», таблица
корректно скроллится только сама по себе (`.table-scroll`).
